### 3. Code Safety & Execution
- **Terminal Check:** After code changes, wait a few seconds and verify terminal output. **NEVER** report a task complete if compilation/build errors exist; fix them first.
- **Git Restrictions:** **NEVER** use commands that discard uncommitted changes (`git restore`, `git reset --hard`, `checkout -- <file>`) without explicit user approval. Check `git status` before drastic fixes.
- **File Editing:** Use exact line matching (`replace_file_content`)—NOT fuzzy matching—for files with repetitive structures (e.g., Angular HTML, large `.ts` files) to prevent corruption.
- **Preserve Unrelated Code:** NEVER remove, rewrite, or refactor unrelated working functions, comments, or imports. Keep edits strictly focused on the requested scope.
- **Database Migrations:** NEVER edit or delete existing applied Django migration files. Always create and apply new forward migrations via `makemigrations`.
- **Cartable Mutations & Concurrency:** ALWAYS wrap status transitions, task claims, and bulk operations in `transaction.atomic()` with `select_for_update()` to prevent race conditions.
- **Excel & Export Standards:** Exports MUST follow the 2-row header architecture (Row 1: Persian display titles, Row 2: Database field keys in light slate font), with `freeze_panes = 'A3'`, and all timestamps converted to Shamsi (`YYYY/MM/DD HH:MM:SS`) via server localtime.
- **Graceful Offline Degradation:** In offline or Lie-Fi states, NEVER throw blocking red error toasts for read/stats endpoints. Use `SKIP_GLOBAL_ERROR_TOAST: true` and preserve local pending records (`_offlinePending`).
- **Real-Time WebSocket Integrity:** Live WebSocket handlers MUST update records in-place without full page reloads, and ALWAYS verify `warehouse_id` before patching.
- **WebSocket Echo & Tab Isolation:** WebSocket echo filtering MUST compare browser client tab/connection IDs (not solely `user_id`), ensuring multi-device usage by the same user updates smoothly without throwing false conflict alerts.
- **PostgreSQL Field Truncation & Rollback Safety:** When restoring, mapping, or rolling back data across different models (e.g. from `Item` to `DocTask`), always clean and truncate string/decimal fields to match destination schema lengths to prevent PostgreSQL `DataError: value too long` aborting transactions.
- **Shamsi Date Parsing Robustness:** Global date utilities must gracefully handle unseparated 8-digit strings (e.g., `14050607`) into standard Shamsi `YYYY/MM/DD` without crashing datepickers or serializers.
- **Sensitive RBAC Protection:** The 6 sensitive permissions (rollback, backup, hard-delete, purge-logs, freeze, factory-reset) MUST remain Superuser-only, excluded from 'Select All', and require explicit confirmation.
- **Browser Testing Default (Type 1 Invariant):** Whenever the user requests a "browser test" (`تست مرورگر`) or "DOM test" (`تست دام`), ALWAYS execute Type 1 by default: Fast Component / DOM Unit Testing (via Vitest & jsdom). NEVER launch heavyweight real-browser E2E automation (Puppeteer, Playwright, or opening actual Chromium windows) unless the user explicitly requests Type 2 / E2E (e.g., "با مرورگر واقعی", "پاپتیر", "تست نوع دوم", "E2E").
- **ng-persian-datepicker & Reactive Forms Invariant (CRITICAL):** In all Angular templates and modals, `<ng-persian-datepicker>` MUST be paired with Angular Reactive Forms (`ReactiveFormsModule`) and an input bound to a `[formControl]`. NEVER use plain `[(ngModel)]` alone without a `FormControl`; `ng-persian-datepicker` discovers its initial view date and renders month day cells (`this.days`) exclusively through `_formControlDirective` / `_formControlName` / `[dateValue]`. Without a `FormControl`, `setFormControl` is never called, causing the popover to open with an empty month/year title and 0 day cells rendered (collapsed grid). Additionally:
  1) **Left-Edge & Modal Anchoring:** For datepickers situated in the leftmost column of a grid or near the left edge of a modal/container (e.g., Column 4 in an `md:grid-cols-4` in RTL layout, or `to-datepicker` / `datepicker-left`), the wrapper or component MUST have class `.to-datepicker` or `.datepicker-left` styled with `left: 0 !important; right: auto !important;`. Otherwise, the default `right: 0` causes the 280px popup to expand leftward and get clipped by parent containers with `overflow-y: auto` / `overflow: hidden`, chopping off Friday (`ج`), Friday date numbers, and the `<` navigation arrow.
  2) **Class Scoping:** NEVER apply the CSS class `.datepicker-outer-container` to static form wrapper elements, as it belongs strictly to the datepicker's internal floating popup.
- **Template Integrity & Diffstat Verification (No Accidental Amputation):** Before reporting any task complete or committing changes, ALWAYS verify `git diff --stat`. If a template edit shows an unexpected large net negative line count (deletions >> additions) where components (tables, modals, action bars) were not explicitly requested to be removed, STOP immediately and verify. Furthermore, NEVER ignore Angular compiler `[WARNING] NG8113: ... is not used within the template`: an NG8113 warning for a component that previously resided in that view is a critical red flag that template sections were accidentally lost during editing, and MUST be investigated and resolved before declaring completion. This check is mechanized by **Guardian 56** (`scripts/e2e/guardian_56_change_integrity.py`): run it with no arguments before **every** commit that touches `frontend/src/app`, and with `--base <commit where the step started>` once at the end of each step. It MUST exit 0. It fails on: event-handler calls removed from a template while the method still exists in the component (accidental amputation), unbalanced tags, `app-tab-bar mobile="icon"` with icon-less tabs, invalid icon names in `.ts` `icon:` fields, and event bindings on project components/directives that are neither a declared output nor a native DOM event (step 7 shipped 33 dead buttons with a non-existent `(actionClick)`; `button[appAction]` uses plain `(click)`). Before using a shared component, read its actual `input()`/`output()` list; never invent inputs or outputs (e.g. `ariaLabel` on `app-tab-bar` does not exist). A genuinely intentional removal is passed with `--allow-removed name1,name2` and each name MUST be justified in the step report. Every file it lists under criterion 2 (net deletion > 80 lines) MUST have its diff re-read and justified in the report.
- **Toolkit Sanctity & Test Runner Isolation:** NEVER modify, hack, or inject decorators/reflection shims (`@Input({ isSignal: true })`, `propMetadata`, etc.) into shared toolbox/infrastructure components (`action-button`, `tab-bar`, `command-center`, `svg-icon.directive`, etc.) merely to satisfy an incompatible or raw test runner (such as standalone Vitest without Angular compiler transforms). Shared toolkit components must strictly remain pure, idiomatic Angular signal code. If a test runner fails to recognize standard Angular signal APIs (`input()`, `output()`), the defect is strictly in the test runner configuration and command (`npx ng test --no-watch --ts-config tsconfig.test21.spec.json --include ...`), NEVER in the shared toolkit.

### 5. Phased Execution & Granular Tasks
- **Mandatory Task Decomposition:** Break down large, multi-step, or complex requests into small, self-contained, and reviewable phases.
- **Step-by-Step Verification:** Implement and verify each phase independently. NEVER proceed to the next phase until the current phase is verified and working without errors.
- **Avoid Bulk Changes:** Avoid large, simultaneous modifications across multiple layers to maintain clean change tracking and rapid debugging.
- **Evidence-Based Completion Reports (No Unverified Claims):** A supervisor (Claude Code) reviews every step against real command output, and in step 6 several reported claims were false. Therefore:
  1) **Every number or "green/passed" claim** (builds, guardians, spec counts, violation counts) MUST come from a command actually run in this session on the **final** tree (after the last edit), and the report MUST quote its summary line verbatim (e.g. `Tests  5 failed | 208 passed (213)`).   2) **Pre-existing failures** must be named with their real cause taken from the log (e.g. `localStorage` undefined in `AuthStore`, NG0201), not a guessed cause.
  3) **Never write "all", "100%", "fully", "every"** unless a command measured it. Prefer exact counts ("22 of 186 remain").

  5) **Reverted or superseded work** (e.g. a change undone in a later commit) MUST be removed from or corrected in the report, not left as a completed item.
  6) **Open items from the previous supervisor review** MUST each be listed with a status (done / not done / deferred with reason). Silently dropping an item is treated as a false claim.
  7) **Self-review of your own diff before reporting:** run `git diff --stat <step start>`; for every template with large net deletions, read the diff hunk and confirm nothing outside the requested scope was removed. Then run Guardian 56 with `--base <step start>`.
- **Reviewers Once Per Phase:** At the end of each phase, before commit, run the relevant reviewer skills once on that phase's diff (`data-loss-reviewer` for offline queue/sync, migrations, delete signals/CASCADE, Service Worker; `tenant-scope-reviewer` for backend views/serializers/querysets/permissions/cartables/reports; `ui-reviewer` for templates/styles/components) and fix confirmed findings.      - *No dynamic tab getters:* `get tabs(): TabDef[]` returning fresh arrays triggers Angular NG0100. Always use `readonly` properties or keyed cache.
     - *Return vs Reject:* Use `appAction="return"` for workflow revision / return for correction (عودت برای اصلاح); use `appAction="reject"` strictly for permanent rejection or revocation.
     - *Visible labels on mobile:* Unfamiliar actions (approve, return, view, send, lock, pay) and modal footers must use `display="label"`.
     - *No static `title` on `button[appAction]`:* The directive automatically derives `title` and `aria-label` from `label`. A `title`, `[title]` or `[attr.title]` on it is overwritten. For a different tooltip (e.g. why the button is disabled) use `[hint]`; `aria-label` stays the label.
     - *`<svg appIcon>` always carries `viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"`:* the directive only fills the inner paths; without these the icon renders cropped and filled black.
     - *Modal invocation order:* When closing a modal and opening another with the same state, invoke the opener first before resetting selected items to `null`.


### 10. Runner Sessions & Lessons (`run_tasks.py`)
A runner session is a conversation started by `run_tasks.py` with one task from `tasks.md`.
- **The runner verifies, not you:** After your turn, the runner itself runs the build, guardians, `ng test` against the session base, `commit-exists` and a clean-tree check, and records the results in `tasks_history.md`.
  - Do not run those yourself: no `ng build`, `ng test`, `npx vitest`, `npx tsc` or guardian runs, not even for a single spec. The only exception is a command the task or plan names for you (e.g. `guardian_55_clickable_ergonomics.py --update-baseline`). If a `[RUNNER]` message reports a failed check, you may re-run that exact failed command to confirm your fix.
  - Never build a base copy with a junction to `node_modules`.
  - For runner sessions this replaces the Guardian 56 runs required by §3 (Template Integrity) and §5 items 1 and 7. Never write a number or a "green" claim for a command you did not run in this session; list such checks under "left to the runner". Reading `git diff --stat <session base>` for your self-review is still required.
- **Never alter, bypass or shadow a runner check:** Do not create, edit or rename anything that changes how a `require:`/`verify:` command behaves: no wrapper or shadow modules (such as an `argparse.py` next to `verify_tools.py`), no edits to `verify_tools.py`, `run_tasks.py` or guardian scripts unless the task explicitly asks, and no rewriting of command arguments. If a check fails and you believe the check itself is wrong (for example a pattern that also matches legitimate code outside your scope), stop, explain why in your report with the evidence, and end your turn; the supervisor fixes the check. Phase 3 session 7 (16 Oct 2026) planted `scripts/automation/argparse.py` to rewrite a `dist-free` pattern; that is a violation even when the code change itself is correct. Untracked `.py` files and anything untracked under `scripts/` now fail `clean-tree`.
- **No status labels:** Never write DONE/FAILED labels such as `[S<N>-DONE]`. The runner marks `[DONE]` in `tasks.md` after its own checks pass.
- **Runner messages:** A message starting with `[RUNNER]` is one of three kinds:
  - **A failed check after your turn:** read the quoted output and the full log, then fix the cause within the original task scope. Commit the fix (only your own files) and end your turn. The runner re-runs every check.
  - **A resume after a model service error:** your turn was cut off by the service, not by your work. Continue exactly where you stopped.
  - **A resume after an Antigravity restart:** the language server restarted mid-turn. Your uncommitted edits are still in the working tree, but your background commands were stopped. Check `git status`, re-read the files you were editing, re-run any command whose result you still need, then continue exactly where you stopped.
- **English with the supervisor (user decision, 15 Oct 2026):** In runner sessions and in supervisor (Claude) review chats, write all replies, reports and commit messages in plain English, without the RTL `<div>` wrapper from §2. Task texts from the supervisor are English too; older Persian tasks stay valid as written. Persian stays mandatory for user-facing app UI text and for replies to the user in normal chats.
- **The "?" rules (§4) do not apply to runner messages:** Task texts and `[RUNNER]` messages are execution requests. A `?` inside code (e.g. a ternary `x ? 'a' : 'b'`) is not a question.
- **Finding plan sections:** Locate a section by its heading (e.g. `## ۹.`), not by searching for a long Persian phrase.
- **Git:**
  - `git add` only the files you changed; never `git add -A` or `git add .`.
  - Never stage `tasks.md`, `run_tasks.*` or `tasks_history.md`.
  - Never push.
- **Dialogue chats (`run_tasks.py ask`):** In a review or agreement chat, answer in the chat only. Do not create or edit any file or artifact, and do not run commands that change the repository.
